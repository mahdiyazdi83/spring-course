## توصیف نتیجه در برابر نوشتن جزئیات پیمایش [#declarative]

<SourceBlock id="heydari-declarative" source="heydari" recording="heydari-02-thursday" timestamp="00:35">

در آغاز صوت، تفاوت دو نگاه به حل مسئله مرور می‌شود: نوشتن جزئیات چگونگی انجام کار و توصیف پردازشی که می‌خواهیم اتفاق بیفتد. مثال، مسیری است که داده را می‌گیرد، فیلتر می‌کند، تبدیل می‌کند و در پایان نتیجه را به شکل فهرست تحویل می‌دهد.

وقتی زنجیرهٔ `filter` و `map` را می‌خوانیم، مراحل موردنظر قابل تشخیص‌اند، بدون اینکه حلقه و مدیریت پیمایش را در همان نقطه نوشته باشیم. شرط فیلتر و رفتار تبدیل هنوز باید مشخص شوند؛ پنهان‌شدن جزئیات پیمایش به معنی حذف آن‌ها از اجرای برنامه نیست.

</SourceBlock>

<GptNote id="gpt-paradigm-boundary">

«توصیفی» و «تابعی» را مترادف کامل نگیرید. زنجیرهٔ Stream می‌تواند شیوهٔ بیان توصیفی داشته باشد، ولی وجود Lambda یا Stream به‌تنهایی کد را به برنامه‌ای با توابع خالص و بدون اثر جانبی تبدیل نمی‌کند. Java همچنان امکان ترکیب سبک‌های مختلف را دارد.

</GptNote>

## رفتار چگونه ورودی یک متد می‌شود؟ [#behavior-contract]

<SourceBlock id="heydari-behavior" source="heydari" recording="heydari-02-thursday" timestamp="02:29">

پرسش مرکزی توضیح این است که چگونه رفتاری را که معمولاً در متد یک شیء تعریف می‌کنیم، به بخش دیگری از برنامه بدهیم. در مرور امکانات Java، نام‌های Lambda، Functional Interface، Method Reference، Stream API و Optional کنار هم مطرح می‌شوند؛ مسیر توضیح از شناخت قرارداد رفتار شروع می‌شود.

در مثال کلاسی، می‌توان یک پیاده‌سازی را به متغیری از نوع interface نسبت داد و آن را به متدی فرستاد که همان interface را به‌عنوان پارامتر می‌گیرد. متد دریافت‌کننده به قرارداد تکیه می‌کند؛ رفتار واقعی را پیاده‌سازی ارسال‌شده تعیین می‌کند. این همان مسئله‌ای است که در [functional interface](/concepts/functional-interface/) و تمرین شرط برنامه‌نویسانِ سه‌شنبه دیده می‌شود.

</SourceBlock>

## anonymous class؛ تعریف پیاده‌سازی در محل استفاده [#anonymous-class]

<SourceBlock id="heydari-anonymous" source="heydari" recording="heydari-02-thursday" timestamp="05:35">

anonymous class به‌عنوان راهی برای تعریف پیاده‌سازی در محل نیاز مرور می‌شود. در توضیح صوت، تعریف کلاس و ساختن نمونه در یک عبارت کنار هم قرار می‌گیرند. لازم نیست برای این رفتار کوتاه، ابتدا یک کلاس نام‌دار جدا تعریف و بعد در نقطه‌ای دیگر از آن نمونه ساخته شود.

سپس روی انتساب آن شیء به نوع interface و ارسالش به یک متد دیگر تأکید می‌شود. از دید استفاده‌کننده، قرارداد interface همچنان ثابت است؛ محل نوشتن پیاده‌سازی تغییر کرده است. این بخش زمینهٔ مقایسه با Lambda را فراهم می‌کند.

</SourceBlock>

## از پیاده‌سازی طولانی به Lambda [#lambda]

<SourceBlock id="heydari-lambda-purpose" source="heydari" recording="heydari-02-thursday" timestamp="15:00">

برای رفتاری ساده مانند بررسی مثبت‌بودن یک عدد، بدنهٔ اصلی تصمیم بسیار کوتاه است، اما شکل anonymous class خطوط بیشتری می‌خواهد. Lambda در این مقایسه راهی است تا توجه خواننده روی ورودی و بدنهٔ همان رفتار بماند.

در ادامهٔ بحث، دلیل انتخاب interface تک‌متد روشن می‌شود: وقتی نوع مقصد تنها یک قرارداد abstract مؤثر دارد، مشخص است بدنهٔ Lambda پیاده‌سازی کدام رفتار است. در صوت، متدهای default از آن قراردادی که باید پیاده‌سازی شود جدا می‌شوند. هدف اصلی، صرفه‌جویی در تعداد خط‌ها نیست؛ مشخص‌شدن رفتار قابل انتقال است.

</SourceBlock>

<GptNote id="gpt-lambda-target">

Lambda در Java به نوع مقصد نیاز دارد. `@FunctionalInterface` شرط functional interface را بررسی می‌کند، اما اجباری نیست. یک anonymous class عمومی با چند متد یا با ارث‌بری از کلاس، الزاماً قابل جایگزینی با Lambda نیست. پیش از کوتاه‌کردن کد، قرارداد interface مقصد را بخوانید.

</GptNote>

<SourceBlock id="heydari-lambda-comparison" source="heydari" recording="heydari-02-thursday" timestamp="16:00">

در مقایسهٔ شفاهی، Lambda معادل کوتاه‌شدهٔ پیاده‌سازی با anonymous class توضیح داده می‌شود و انجام کارهای پشت‌صحنه به کامپایلر نسبت داده می‌شود. این قیاس به فهمِ ارسال همان رفتار کوتاه کمک می‌کند، اما برای توضیح دقیق مدل زبان و نحوهٔ ترجمه کافی نیست.

</SourceBlock>

## interfaceهای آماده و مثال Consumer [#builtins]

<SourceBlock id="heydari-builtins" source="heydari" recording="heydari-02-thursday" timestamp="21:00">

بعد از interfaceهای تک‌رفتار، چهار خانوادهٔ آمادهٔ `Predicate`، `Function`، `Consumer` و `Supplier` مرور می‌شوند. محور دسته‌بندی، ورودی و خروجی رفتار است: آیا مقداری می‌گیرد؟ آیا نتیجه‌ای می‌دهد؟ نتیجه از چه نوعی است؟ لازم نیست برای هر رفتار کوتاه، interface جدیدی با نام دیگری ساخته شود.

برای `Consumer` مثال عملیاتی روی حساب مطرح می‌شود: یک حساب دریافت می‌شود و عملیاتی روی آن انجام می‌گیرد، بدون اینکه مقدار بازگشتی داشته باشد. مراحل بررسی و تغییر وضعیت حساب برای نشان‌دادن تفاوت جزئیات پیاده‌سازی با نام‌گذاری یک رفتار بزرگ‌تر به‌کار می‌روند. این مثال، طرح یک سامانهٔ بانکی یا دستور اجرایی کامل آن نیست.

</SourceBlock>

<GptNote id="gpt-builtins-recap">

برای مرور قراردادها: `Predicate<T>` ورودی را با `test` به `boolean` تبدیل می‌کند؛ `Function<T,R>` با `apply` مقدار تبدیل‌شده می‌دهد؛ `Consumer<T>` با `accept` مقدار را مصرف می‌کند و خروجی `void` دارد؛ `Supplier<T>` بدون ورودی با `get` مقدار تولید می‌کند. `void` به معنی «هیچ کاری انجام نمی‌شود» نیست؛ چاپ یا تغییر وضعیت می‌تواند اثر رفتار باشد. جدول کامل‌تر در [درس سه‌شنبه](/tuesday/session-02/#functional-interfaces) آمده است.

</GptNote>

## کاربرد قرارداد در filter و Stream [#filter-contract]

<SourceBlock id="heydari-filter" source="heydari" recording="heydari-02-thursday" timestamp="29:20">

پرسش اصلی پایان مرور این است: `filter` خودش یک متد است، پس چرا از ما رفتار دیگری می‌خواهد؟ سازوکار عمومی فیلترکردن در API وجود دارد، ولی شرط انتخاب هر عنصر مخصوص مسئلهٔ استفاده‌کننده است. برنامه‌نویس آن شرط را در قالب `Predicate` به متد می‌دهد.

با این نگاه، ارسال Lambda به `filter` صرفاً یک شکل نوشتاری کوتاه نیست؛ بخش متغیرِ تصمیم‌گیری از سازوکار عمومی پردازش جدا شده است. برای خواندن سایر متدهای Stream نیز ابتدا نوع رابطی را که می‌گیرند بررسی کنید و بعد بپرسید رفتار ارسال‌شده در کدام مرحله استفاده می‌شود. مسیر کامل این مثال‌ها در [Stream Pipeline](/concepts/stream-pipeline/) آمده است.

</SourceBlock>

<GptNote id="gpt-chain-vs-stream">

هر زنجیرهٔ فراخوانی متد، Stream API نیست. شکل فرضیِ «انتقال مانده و سپس بستن حساب» برای توضیح ترکیب مراحل کمک می‌کند، اما باید نوع و قرارداد هر متد واقعی را جدا بررسی کرد. در Stream، `filter` انتخاب را بیان می‌کند، `map` تبدیل را و عملیات نهایی مصرف نتیجه را.

</GptNote>

## پرسش پایانی و مرور پیشنهادی [#review]

<SourceBlock id="heydari-study-priority" source="heydari" recording="heydari-02-thursday" timestamp="32:35">

در پایان، پرسشی دربارهٔ Container در Spring و Jakarta مطرح می‌شود و نام‌های IoC Container و Servlet Container از هم تفکیک می‌شوند. صوت وارد آموزش تفصیلی سازوکار آن‌ها نمی‌شود؛ گفت‌وگو بیشتر دربارهٔ تعیین اولویت مطالعه و تفاوت «شناخت تعریف» با «نیاز به تمرین عملی» است.

جمع‌بندی مرور برنامه‌نویسی تابعی نیز این است که امکانات آشنای API را با درک قراردادشان استفاده کنیم: اگر متدی Consumer یا Function می‌خواهد، بدانیم چه رفتاری را به آن می‌سپاریم. این صفحه، بحث Container را به‌عنوان موضوع تدریس‌شدهٔ کامل معرفی نمی‌کند.

</SourceBlock>

</SourceBlock>
