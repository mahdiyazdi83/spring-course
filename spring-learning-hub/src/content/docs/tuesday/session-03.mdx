## ۱. مسئله: وابستگی کجا شکل می‌گیرد؟ [#coupling]

<SourceBlock id="teacher-coupling" source="teacher" recording="teacher-03-part1" timestamp="00:00" summary="وابستگی فقط یک import نیست؛ تغییر طراحی، نیازهای build و در دسترس‌بودن سرویس در زمان اجرا می‌توانند اجزای برنامه را به هم وابسته کنند.">

استاد coupling را از سه زاویه باز می‌کند:

| زاویه      | پرسش اصلی                                               | مثال مطرح‌شده                                                |
| ---------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| زمان طراحی | تغییر یک جزء چه تغییری در طراحی مصرف‌کننده لازم می‌کند؟ | سرویس A مستقیماً پیاده‌سازی سرویس B را می‌شناسد.             |
| زمان ساخت  | ساخت و بسته‌بندی یک ماژول به چه چیزهایی نیاز دارد؟      | وابستگی‌هایی که ابزار build مانند Maven مدیریت می‌کند.       |
| زمان اجرا  | اجرا یا خرابی یک جزء چطور روی جزء دیگر اثر می‌گذارد؟    | پایین‌بودن درگاه پرداخت، مسیر درخواست برنامه را مختل می‌کند. |

در ادامهٔ درس، تمرکز روی کاهش وابستگی طراحی در مثال Java است. ابتدا کلاس مصرف‌کننده مستقیماً پیاده‌سازی را می‌سازد. قدم بعدی استفاده از interface است؛ سپس ساخت شیء به Factory سپرده می‌شود. این قدم‌ها محل وابستگی را تغییر می‌دهند، اما هنوز باید مشخص کنیم چه کسی همکار موردنیاز را به مصرف‌کننده می‌رساند.

</SourceBlock>

<GptNote id="gpt-coupling" context="teacher-coupling">

استفاده از interface تضمین نمی‌کند که هیچ تغییری به مصرف‌کننده سرایت نکند؛ تغییر قرارداد یا رفتار سرویس همچنان مهم است. همچنین DI به‌تنهایی مشکل قطع‌شدن درگاه پرداخت را حل نمی‌کند. موضوع این بخش، جداکردن **انتخاب و ساخت پیاده‌سازی** از **منطق استفاده از آن** است.

</GptNote>

## ۲. DI و IoC؛ جابه‌جایی مسئولیت ساخت [#dependency-injection]

<SourceBlock id="teacher-di" source="teacher" recording="teacher-03-part1" timestamp="09:00" summary="در تزریق وابستگی، مصرف‌کننده نیازش را مشخص می‌کند و یک بخش بیرونی شیء مناسب را ساخته و در اختیارش می‌گذارد.">

در [Dependency Injection](/concepts/dependency-injection/)، مصرف‌کننده منتظر دریافت همکار است؛ مسئولیت انتخاب، ساخت و اتصال آن به بخش بیرونی منتقل می‌شود. استاد این مسئله و راه‌حل را به‌عنوان یک الگوی طراحی توضیح می‌دهد و تأکید می‌کند که می‌توان آن را با Java معمولی هم پیاده کرد.

تفاوت با Factory از دید مصرف‌کننده روشن می‌شود: در حالت Factory، کلاس خودش سراغ سازندهٔ اشیا می‌رود و درخواست می‌دهد؛ در حالت DI، وابستگی به کلاس تحویل داده می‌شود. بحث IoC یا وارونگی کنترل نیز همین جابه‌جایی جهت کنترل را توضیح می‌دهد: تمام کارها از داخل مصرف‌کننده آغاز نمی‌شوند.

استاد برای تصویرسازی context، محلی را در نظر می‌گیرد که اشیا را با شناسه نگه می‌دارد و امکان دسترسی و اتصال آن‌ها را فراهم می‌کند. تعبیر «context pattern» در این بخش، نام‌گذاری آموزشی خود اوست؛ نباید آن را نام قطعی یک الگوی GoF تلقی کرد.

</SourceBlock>

<GptNote id="gpt-injection-shapes" context="teacher-di">

سازنده و setter دو مسیر اصلی و روشن برای دریافت وابستگی‌اند. در همین کدهای جلسه، تزریق روی **فیلد** هم دیده می‌شود: نمونهٔ دستی با Reflection فیلد را مقداردهی می‌کند و نمونهٔ Spring از `@Autowired` روی فیلد استفاده می‌کند. پس DI را به وجود setter یا annotation خاص محدود نکنید.

</GptNote>

<SourceBlock id="teacher-ecosystem" source="teacher" recording="teacher-03-part1" timestamp="26:30">

در مرور اکوسیستم، DI و AOP به‌عنوان دو پایهٔ مهم Spring مطرح می‌شوند؛ پروژه‌هایی مانند Data و Security هر کدام مسئلهٔ مشخصی را دنبال می‌کنند. سپس در مقایسهٔ تاریخی با EJB، سادگی کار با اشیای معمولی Java و کاهش کارهای تکراری برجسته می‌شود.

هدف این مرور، توضیح علت شروع دوره با Spring Framework است: قبل از راحتی راه‌اندازی و تنظیمات خودکار Spring Boot، باید بفهمیم کانتینر چه می‌کند. اشاره‌های کلاس به رقبا و سرعت آن‌ها، بحث مقایسه‌ای کلاس است و در این درس به‌عنوان نتیجهٔ benchmark بازنشر نمی‌شود.

</SourceBlock>

<SourceBlock id="teacher-standards" source="teacher" recording="teacher-03-part1" timestamp="43:30" summary="در مقایسهٔ لایه‌های برنامه، استاد بر شناخت استاندارد، API و پیاده‌سازی تأکید می‌کند و Spring MVC را در این بخش به‌صورت wrapper روی Jersey توصیف می‌کند.">

مرور لایه‌های داده، سرویس و وب به تفکیک **استاندارد، API و پیاده‌سازی** می‌رسد. متن specification قرارداد را برای پیاده‌ساز مشخص می‌کند و API سطح استفادهٔ برنامه‌نویس است؛ برای نمونه، Jersey در بحث Jakarta REST و Weld در بحث CDI معرفی می‌شوند. در همین مقایسه، Spring MVC به‌صورت wrapper روی Jersey توصیف می‌شود؛ این بخش به اصلاح زیر نیاز دارد.

</SourceBlock>

<TechnicalCorrection id="correction-mvc-jersey" corrects="teacher-standards" statement="Spring MVC یک wrapper است که درون آن Jersey قرار دارد." correction="Spring MVC فریم‌ورک وب Spring بر پایهٔ Servlet API است؛ پیاده‌سازی آن wrapper روی Jersey نیست." reason="مشترک‌بودن بعضی نیازها یا زیرساخت Servlet به معنی یکی‌بودن مدل برنامه‌نویسی و پیاده‌سازی این دو نیست.">

برای فهم نقش Spring در این درس، روی قراردادهای مشترک و مسئولیت هر لایه تمرکز کنید و این قیاس را به رابطهٔ وابستگی کتابخانه‌ها تعمیم ندهید. [معرفی رسمی Spring Web MVC](https://docs.spring.io/spring-framework/reference/web/webmvc.html)

</TechnicalCorrection>

## ۳. کانتینر دستی؛ پشت صحنهٔ تزریق [#manual-container]

<SourceBlock id="teacher-manual" source="teacher" summary="MyContext نام پیاده‌سازی بانک را از فایل می‌خواند، شیء می‌سازد و آن را در فیلد علامت‌خوردهٔ BankClient قرار می‌دهد.">

پروژهٔ `dependencyInjection` عمداً بدون Spring نوشته شده است. `BankClient` به `ITransferService` نیاز دارد؛ `MeliImpl` و `MellatImpl` دو پیاده‌سازی آموزشی‌اند. متد انتقال این کلاس‌ها فقط پیام چاپ می‌کند و تراکنش واقعی بانکی انجام نمی‌دهد.

در نسخهٔ فعال کد، مصرف‌کننده به‌جای ساخت مستقیم بانک، فیلد خود را با annotation سفارشی مشخص می‌کند. بخش‌های کامنت‌شدهٔ همان فایل، مسیر قبلیِ ساخت مستقیم و Factory را نگه داشته‌اند.

</SourceBlock>

جریان `MyContext` را در دو مرحله بخوانید:

1. `getBean("bank")` فایل تنظیمات را می‌خواند، نام کلاس را پیدا می‌کند و با `Class.forName` و سازندهٔ بدون آرگومان نمونه می‌سازد.

## ۷. تعریف Bean، نام و مقداردهی [#bean-definition]

<SourceBlock id="teacher-bean-definition" source="teacher" summary="در XML می‌توان چند تعریف از یک کلاس داشت، برای Bean نام گذاشت و ورودی سازنده و propertyهای آن را جدا پیکربندی کرد.">

[Bean](/concepts/bean/) را از کلاس و تعریف آن جدا کنید. در `config.xml` زیر، دو تعریف مستقل از `BeanOne` وجود دارد؛ یک تعریف دیگر نیز `BeanTwo` را با نام `two` معرفی می‌کند. اجرای کانتینر این فایل، سه بار پیام سازنده‌ها را چاپ کرد.

وقتی نام صریح نداده‌ایم، کانتینر برای تعریف نام تولید می‌کند. این با alias متفاوت است: چند alias می‌توانند به یک Bean اشاره کنند، اما دو تعریف مستقل لزوماً یک شیء نیستند.

در ضبط، چند نام برای یک Bean امتحان می‌شود و سپس با `getBeansOfType` و `getAliases` نتیجه بررسی می‌شود. پیمایش Map با Stream و `forEach` نیز به مباحث جلسهٔ قبل برمی‌گردد. کاربرد مورد بحث alias این است که همان شیء در نقاط مختلف با نام معنادار مناسب آن بخش قابل دریافت باشد؛ قرار نیست برای هر نام یک نمونهٔ تازه بسازیم.

نسخهٔ نهایی `p03beanNames/config.xml` فقط یک Bean بدون نام صریح نگه داشته است؛ حالت‌های آزمایش‌شدهٔ alias در ویدیو را نباید عین کد نهایی مخزن معرفی کرد. کلاس `Context` همچنان دریافت Beanها بر اساس نوع و چاپ نام و alias را نشان می‌دهد.

تولید نام پیش‌فرض در پایان این بخش با اصل Convention over Configuration توضیح داده می‌شود: وقتی تنظیم صریحی ندهیم، قرارداد پیش‌فرض بخشی از کار را انجام می‌دهد. برای نام‌های مورد استفادهٔ برنامه، نام‌گذاری روشن و پرهیز از برخورد نام‌ها همچنان مهم است.

</SourceBlock>

<GptNote id="gpt-bean-capabilities" context="teacher-bean-definition">

مدیریت‌شدن یک شیء در کانتینر، زمینهٔ استفاده از قابلیت‌های Spring را فراهم می‌کند؛ اما Bean شدن به‌تنهایی همهٔ قابلیت‌های امنیت، تراکنش و ثبت رخداد را خودکار فعال نمی‌کند. هر قابلیت، وابستگی و پیکربندی متناسب خودش را می‌خواهد. در این مثال‌های کوچک، فعلاً ساخت و اتصال اشیا را مشاهده می‌کنیم.

همچنین singleton در Spring به هر **تعریف Bean در هر کانتینر** مربوط است؛ دو تعریف از یک کلاس یا دو کانتینر مستقل می‌توانند نمونه‌های جدا داشته باشند. چند بار چاپ‌شدن سازنده در این وضعیت، پیش‌فرض singleton را نقض نمی‌کند. [مرجع scopeها](https://docs.spring.io/spring-framework/reference/core/beans/factory-scopes.html)

</GptNote>

این دو namespace شکل کوتاه‌تر پیکربندی سازنده و property هستند؛ نمونه‌های بلندتر `constructor-arg` و `property` در کامنت‌های فایل حفظ شده‌اند. بخش `p02annotationxml` در snapshot این جلسه فقط یک کلاس خالی دارد؛ هنوز مثال کامل آن روش نیست.

## ۸. BeanFactory و ApplicationContext چه تفاوتی دارند؟ [#factory-vs-context]

<SourceBlock id="teacher-factory" source="teacher" summary="نمونهٔ BeanFactoryVSApplicationContext زمان آماده‌شدن Product را پس از خواندن XML و پس از درخواست Bean مقایسه می‌کند.">

پروژهٔ `BeanFactoryVSApplicationContext` با **Spring Context 6.1.3** دو مسیر را مقایسه می‌کند. در مسیر اول، `XmlBeanDefinitionReader` تعریف‌ها را وارد `DefaultListableBeanFactory` می‌کند؛ در مسیر دوم، `ClassPathXmlApplicationContext` راه‌اندازی کامل‌تری را انجام می‌دهد.

## ۹. ثبت processor با اجرای callback یکی نیست [#post-processors]

<SourceBlock id="teacher-processors" source="teacher" summary="مثال دوم دو processor را در XML تعریف می‌کند و booleanهایی را چاپ می‌کند که داخل callbackهای آن‌ها تغییر می‌کنند.">

مثال دوم پروژه برای بررسی رفتار خودکار processorهاست. `C01MyBeanFactoryPostProcessor` در `postProcessBeanFactory` پرچم خود را تغییر می‌دهد و `C02MyBeanPostProcessor` این کار را در `postProcessBeforeInitialization` انجام می‌دهد. نام پرچم‌ها شامل `Registered` است، اما محل تغییر مقدارشان، **داخل callback** است.

XML ذخیره‌شده فقط همین دو processor را معرفی می‌کند. کد `C04ApplicationContextDemo` پس از ساخت کانتینر، هر دو را با `getBean` می‌گیرد و پرچم‌ها را چاپ می‌کند.

در اجرای دقیق نمونه با Spring 6.1.3، مسیر Factory خروجی `false / false` و مسیر Context خروجی `true / false` داد. بررسی مستقل فهرست processorهای کانتینر، حضور `C02MyBeanPostProcessor` را تأیید کرد؛ ساخت یک Bean عادی از طریق `createBean(Object.class)` نیز پرچم دوم را به `true` تغییر داد. این بررسی تکمیلی توسط GPT انجام شده و بخشی از کد استاد نیست.

در یک Factory ساده، processorها با صرف خواندن تعریف XML خودکار فعال نمی‌شوند. ApplicationContext راه‌اندازی و ثبت خودکار را انجام می‌دهد؛ `BeanFactoryPostProcessor` با تعریف‌ها کار می‌کند و `BeanPostProcessor` با نمونه‌های در حال مقداردهی. [مقایسهٔ رسمی BeanFactory و ApplicationContext](https://docs.spring.io/spring-framework/reference/core/beans/beanfactory.html)
