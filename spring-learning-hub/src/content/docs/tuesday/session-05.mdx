## Lazy و DependsOn؛ زمان ساخت و ترتیب آماده‌سازی [#lazy-depends-on]

<SourceBlock id="lazy-recap" source="teacher" recording="teacher-05-part1" timestamp="00:00">

استاد بحث را با ساخت eagerِ singletonهای معمول و تغییر آن با `lazy-init` ادامه می‌دهد. انتخاب lazy یا eager یک trade-off است: صرفاً برچسب «بهتر» و «بدتر» ندارد و باید با نیاز برنامه و هزینهٔ آماده‌سازی سنجیده شود. وقتی هر سه Bean در XML lazy باشند، شروع کانتینر آن‌ها را نمی‌سازد؛ دریافت BeanOne، ساخت آن را لازم می‌کند.

اگر BeanOne به BeanTwo و BeanThree وابستگی ترتیب داشته باشد، `depends-on` اعلام می‌کند آن دو باید پیش از BeanOne آماده شوند، حتی اگر خودشان lazy باشند. این موضوع ادامهٔ [مثال جلسهٔ چهارم](/tuesday/session-04/#depends-on) است؛ این جلسه همان تنظیم را با annotation و Java Config نشان می‌دهد.

</SourceBlock>

<CodeExample
  id="depends-annotation"
  source="teacher"
  lang="java"
  filename="BeanOne.java"
  repositoryPath="session5/src/main/java/ir/digixo/p01dependon/p02annotation/BeanOne.java"

    'package ir.digixo.p01dependon.p02annotation;\n\n\nimport org.springframework.context.annotation.DependsOn;\nimport org.springframework.context.annotation.Lazy;\nimport org.springframework.stereotype.Component;\n\n@Component\n@Lazy\n@DependsOn({"beanTwo","beanThree"})\npublic class BeanOne {\n    public BeanOne() {\n        System.out.println("bean one created");\n    }\n}'
  }
/>

<SourceBlock id="depends-java" source="teacher" recording="teacher-05-part1" timestamp="04:30">

در Java Config می‌توان `@Lazy` و `@DependsOn` را روی متد `@Bean` گذاشت. قرار دادن `@Lazy` روی کلاس configuration نیز پیش‌فرض lazy را برای Beanهای تعریف‌شده در آن اعلام می‌کند. استاد نسخهٔ class-based را به‌صورت طرح کوتاه می‌نویسد؛ مقصود، محل annotationهاست.

</SourceBlock>

<CodeExample
  id="depends-method"
  source="teacher"
  lang="java"
  filename="Config.java"
  repositoryPath="session5/src/main/java/ir/digixo/p01dependon/p03class/Config.java"
  caption="طرح ذخیره‌شده: DependsOn روی متد هنوز نام وابستگی ندارد."
  code={
    'package ir.digixo.p01dependon.p03class;\n\nimport org.springframework.context.annotation.Bean;\nimport org.springframework.context.annotation.Configuration;\nimport org.springframework.context.annotation.DependsOn;\nimport org.springframework.context.annotation.Lazy;\n\n@Configuration\n//@Lazy\npublic class Config {\n\n\n    @Bean\n    @Lazy\n    @DependsOn\n    public BeanOne beanOne()\n    {\n        return new BeanOne();\n    }\n}'
  }
/>

<SourceBlock id="depends-snapshot" source="gpt">

در snapshot، `@DependsOn` متد بالا آرایهٔ نام‌ها ندارد؛ بنابراین وابستگی به BeanTwo و BeanThree را اعلام نمی‌کند. همچنین launcherهای annotation و class هنوز مسیر XML جلسهٔ چهارم را دارند. برای اجرای همان سناریو باید کانتکست و نام Beanهای همین پکیج را تنظیم کرد؛ اجرای launcher قدیمی شاهدی برای کارکرد annotationهای جدید نیست.

در بررسی XML همین جلسه، پیش از `getBean` هیچ‌یک از سه singleton ساخته نشده بود و درخواست BeanOne، ابتدا پیام BeanTwo و BeanThree و سپس BeanOne را چاپ کرد. `depends-on` ترتیب آماده‌سازی است؛ خودش جای constructor injection یا setter injection را نمی‌گیرد.

</SourceBlock>

## وابستگی اختیاری؛ required=false و مسئولیت مصرف‌کننده [#optional-dependencies]

<SourceBlock id="required-demo" source="teacher" recording="teacher-05-part1" timestamp="07:30">

در مثال MyService و MyDao، setter با `@Autowired` مشخص می‌شود و کانتینر هر دو Component را پیدا می‌کند. با حذف `@Component` از MyDao، وابستگی اجباری پیدا نمی‌شود و startup شکست می‌خورد. صرف انتخاب setter injection، وابستگی را اختیاری نمی‌کند.

سپس `required=false` اجازه می‌دهد سرویس بدون DAO ساخته شود. خطا در مثال بعداً و هنگام استفاده از DAO رخ می‌دهد: مقدار `myDao` همچنان `null` است و فراخوانی `bean.getMyDao().create()` به آن دسترسی پیدا می‌کند. اختیاری‌کردن اتصال، مسئولیت تصمیم‌گیری دربارهٔ نبودن وابستگی را به منطق مصرف‌کننده می‌سپارد.

</SourceBlock>

<CodeExample
  id="optional-setter"
  source="teacher"
  lang="java"
  filename="MyService.java"

    'package ir.digixo.p02required;\n\nimport org.springframework.beans.factory.annotation.Autowired;\nimport org.springframework.lang.Nullable;\nimport org.springframework.stereotype.Component;\n\nimport java.util.Optional;\n\n@Component\npublic class MyService {\n\n    private MyDao myDao;\n\n\n    public MyService() {\n        System.out.println("service obj created!!!!");\n    }\n\n\n    public MyDao getMyDao() {\n        return myDao;\n    }\n\n    @Autowired(required = false)\n    public void setMyDao(MyDao myDao) {\n        this.myDao = myDao;\n    }\n\n\n}'
  }
/>

<SourceBlock id="optional-version-claim" source="teacher" recording="teacher-05-part1" timestamp="15:00">

در ادامه، هنگام آزمایش `@Nullable` و `Optional`، استاد از تغییرات Spring 7 و باقی‌ماندن راه `required=false` صحبت می‌کند. این جمع‌بندی از آزمایش همان لحظه آمده است؛ نتیجهٔ نسخهٔ واقعی را باید جدا بررسی کرد.

</SourceBlock>

[مرجع رسمی Autowired](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)

</TechnicalCorrection>

<SourceBlock id="optional-verification" source="gpt">

در یک آزمایش مستقل با Spring 7.0.9، setter دارای `Optional<Dependency>` بدون Bean متناظر، `Optional.empty()` گرفت؛ setter دارای پارامتر `org.jspecify.annotations.Nullable` نیز با `null` فراخوانی شد. در مقابل، setter با `@Autowired(required=false)` در نبود وابستگی اصلاً فراخوانی نمی‌شود. برای مرور خود نوع Optional به [مرجع Optional](/concepts/optional/) مراجعه کنید.

</SourceBlock>

استاد بررسی معادل XML را به تمرین واگذار می‌کند و از یافتن attribute متناظر صحبت می‌کند. این بخش یک اجرای کامل XML در ضبط ندارد.

</SourceBlock>

<TechnicalCorrection id="required-xml-correction" corrects="required-xml-exercise" statement="برای اختیاری‌کردن وابستگی در XML، یافتن attribute با نام required پیشنهاد می‌شود." correction="در تعریف استاندارد bean یا property در Spring XML، required=false معادل مستقیمی برای attribute این annotation نیست. رفتار autowire و ارجاع صریح ref را باید جدا بررسی کرد؛ ref به Bean ناموجود همچنان خطاست." reason="کپی نام attribute از annotation به XML می‌تواند فایل پیکربندی نامعتبر بسازد.">

## Mixed configuration؛ انتخاب نقطهٔ شروع [#mixed-configuration]

<SourceBlock id="mixed-motivation" source="teacher" recording="teacher-05-part1" timestamp="18:00">

در پروژهٔ legacy یا هنگام ادغام دو پروژه، ممکن است بخشی از Beanها در XML و بخشی در Java تعریف شده باشند. لازم نیست برای ورود یک بخش، همهٔ تنظیمات آن را فوراً بازنویسی کنیم. پرسش اصلی این است که کدام تنظیم نقطهٔ شروع کانتینر باشد: XML-centric یا class-centric.

در مرور پیش‌نیاز این بحث، استاد دوباره تفاوت شناسایی Componentها با داشتن صرفِ annotation را یادآوری می‌کند: ComponentScan محدودهٔ جست‌وجو را تعیین می‌کند. قرار دادن آن روی کلاس configuration، محل تنظیم این رفتار را روشن نگه می‌دارد.

</SourceBlock>

<SourceBlock id="xml-centric" source="teacher" recording="teacher-05-part1" timestamp="24:00">

در نسخهٔ XML-centric، `FileSystemXmlApplicationContext` فایل `config1.xml` را می‌خواند. این فایل BeanOne را ثبت می‌کند، با `<import resource="config2.xml"/>` تعریف BeanTwo را می‌آورد و با component scanning کلاس‌های configuration را پیدا می‌کند. `@Configuration` نیز از خانوادهٔ Component است؛ پس متد `@Bean` مربوط به BeanThree وارد همان کانتینر می‌شود. صرف وجود کلاس BeanFour در پکیج برای ثبت آن کافی نیست؛ در این مثال تعریفی برای آن نوشته نشده است.

</SourceBlock>

<CodeExample id="mixed-xml" source="teacher" lang="xml" filename="config1.xml" repositoryPath="session5/src/main/java/ir/digixo/p03MixConfig/p01Xml/config1.xml" caption="XML اصلی: import فایل دوم و scan کلاس‌های configuration." code={"<?xml version=\"1.0\" encoding=\"UTF-8\"?>\n<beans xmlns=\"http://www.springframework.org/schema/beans\"\n       xmlns:xsi=\"http://www.w3.org/2001/XMLSchema-instance\"\n       xmlns:context=\"http://www.springframework.org/schema/context\"\n       xsi:schemaLocation=\"http://www.springframework.org/schema/beans\n       http://www.springframework.org/schema/beans/spring-beans.xsd http://www.springframework.org/schema/context https://www.springframework.org/schema/context/spring-context.xsd\">\n\n    <!--business obj-->\n\n\n\n\n\n    <bean class=\"ir.digixo.p03MixConfig.p01Xml.BeanOne\"/>\n\n    <import resource=\"config2.xml\"/>\n\n    <context:component-scan base-package=\"ir.digixo.p03MixConfig.p01Xml\"/>\n\n\n\n\n\n\n\n\n</beans>"} />

<SourceBlock id="class-centric" source="teacher" recording="teacher-05-part1" timestamp="30:00">

در نسخهٔ class-centric، شروع کار با `AnnotationConfigApplicationContext(Config1.class)` است. `@Import(Config2.class)` کلاس configuration دیگر را وارد می‌کند؛ `@ImportResource` فایل XML را می‌خواند. XML واردشده می‌تواند خودش XML دیگری را import کند. بنابراین شکل شروع کانتینر با قالب تمام منابعی که در نهایت مصرف می‌کند یکی نیست.

مسیرهای `file:` در نمونه به سیستم استاد وابسته‌اند. برای اجرای محلی باید آن‌ها را به محل واقعی منبع تغییر دهید یا فایل‌های موردنیاز را به resources ببرید و از مسیر classpath مناسب استفاده کنید؛ صرف تغییر پیشوند مسیر، فایل را وارد خروجی build نمی‌کند.

</SourceBlock>

## Stereotypeها و مسئولیت لایه‌ها [#stereotypes]

<SourceBlock id="stereotype-intro" source="teacher" recording="teacher-05-part1" timestamp="34:10">

تا اینجا همهٔ نقش‌ها با `@Component` معرفی شده‌اند. اکنون استاد ساختار Controller → Service → DAO را باز می‌کند: Controller نقطهٔ ورود/ارائه، Service محل منطق کسب‌وکار و DAO محل دسترسی به داده است. این تفکیک را هم در ساختارهای monolithic و هم داخل یک سرویس می‌توان دید. نام‌هایی مثل MySqlDao و OracleDao در این تمرین برای مقایسهٔ پیاده‌سازی‌ها هستند؛ نام‌گذاری واقعی باید مسئولیت دامنه، مثلاً Product، را هم روشن کند.

</SourceBlock>

<SourceBlock id="stereotype-wiring" source="teacher" recording="teacher-05-part1" timestamp="39:00">

Controller به interfaceِ Service وابسته است و ProductService به interfaceِ Dao. چون دو DAO وجود دارد، انتخاب پیاده‌سازی لازم است: در این مثال `@Inject` همراه `@Named("mySqlDao")` روی پارامتر setter استفاده می‌شود. Controller فقط یک Service متناظر دارد و به qualifier اضافی نیاز ندارد. فراخوانی `create()` در Controller، به `createProduct()` در Service و سپس `create()` در DAO می‌رسد.

پس از اجرای زنجیره، `@Component`های عمومی به `@Controller`، `@Service` و `@Repository` تبدیل می‌شوند. در همین برنامهٔ ساده خروجی تغییر نمی‌کند؛ نام annotation مسئولیت کلاس را برای خواننده روشن می‌کند. تعارض نام interfaceِ `Service` با annotation نیز دلیل استفادهٔ نمونه از نام کامل `@org.springframework.stereotype.Service` است.

</SourceBlock>

## Custom scanning؛ تعیین معیار شناسایی Bean [#custom-scanning]

<SourceBlock id="scan-options" source="teacher" recording="teacher-05-part1" timestamp="51:00">

ComponentScan فقط نام یک پکیج نیست؛ گزینه‌هایی مانند name generator، scope resolver، resource pattern و filter دارد. کلاس روی `includeFilters` تمرکز می‌کند و چند معیار را آزمایش می‌کند:

| FilterType        | معیار این تمرین                                             |
| ----------------- | ----------------------------------------------------------- |
| `ANNOTATION`      | شناسایی کلاس علامت‌خورده با MyAnnotation                    |
| `ASSIGNABLE_TYPE` | شناسایی پیاده‌سازهای MyInterface                            |
| `REGEX`           | تطبیق نام کلاس با الگو                                      |
| `ASPECTJ`         | تطبیق type pattern؛ نیازمند کتابخانهٔ مربوط                 |
| `CUSTOM`          | در فهرست گزینه‌ها معرفی می‌شود؛ اینجا پیاده‌سازی کامل ندارد |

MyAnnotation با targetِ TYPE و retentionِ RUNTIME تعریف می‌شود. سپس با تغییر معیار به MyInterface، حتی کلاس بدون Component نیز می‌تواند candidate باشد. interface در این نمونه marker است و متدی ندارد؛ هدفش تعیین عضویت در گروه قابل شناسایی است.

</SourceBlock>

## Bean lifecycle؛ آماده‌سازی با ساخت شیء یکی نیست [#bean-lifecycle]

<SourceBlock id="lifecycle-background" source="teacher" recording="teacher-05-part2" timestamp="02:20">

استاد lifecycle را با تجربهٔ Java و Servlet مقایسه می‌کند: JVM حافظهٔ شیء را مدیریت می‌کند، اما framework برای آماده‌سازی، استفاده و جمع‌کردن منابع قراردادهای خودش را دارد. در Servlet، `init`، `service` و `destroy` نمونهٔ آشنای این قرارداد هستند. در Spring نیز Bean فقط خروجی `new` نیست؛ وابستگی‌هایش باید متصل شوند و callbackهای مربوط به آماده‌سازی آن اجرا شوند.

نمودار کلاس چند مرحله را کنار هم می‌گذارد: ساخت، تزریق، دریافت اطلاعات کانتینر از طریق Awareها، callbackهای initialization و در پایان callbackهای destruction. هدف، حفظ‌کردن تعداد ثابتی از مراحل نیست؛ برای توسعهٔ برنامه باید بدانیم منطق آماده‌سازی و آزادسازی منابع را کجا قرار دهیم، و برای کار روی خود framework شناخت جزئیات بیشتری لازم است.

</SourceBlock>

<SourceBlock id="lifecycle-boundaries" source="gpt">

callbackِ destruction به معنی حذف فوری شیء از حافظه نیست. `close()` کانتینر فرصت آزادکردن منابع Beanهای تحت مدیریت را فراهم می‌کند؛ تصمیم GC دربارهٔ حافظه موضوع دیگری است. همچنین قیاس با Servlet به این معنی نیست که هر Spring Bean یک متد `service()` مخصوص رسیدگی به درخواست دارد.

مسیر ساده برای این مثال‌ها چنین است: **ساخت شیء → تزریق وابستگی‌ها → initialization → استفاده → بستن کانتینر و cleanup**. زمان ساخت می‌تواند تحت تأثیر lazy باشد. برای مرور متمرکز به [Bean lifecycle](/concepts/bean-lifecycle/) مراجعه کنید.

</SourceBlock>

## سه راه تعریف callbackهای initialization و destruction [#lifecycle-callbacks]

<SourceBlock id="lifecycle-interfaces" source="teacher" recording="teacher-05-part2" timestamp="18:00">

راه اول پیاده‌سازی `InitializingBean` و `DisposableBean` است. متد `afterPropertiesSet()` پس از تنظیم وابستگی‌ها اجرا می‌شود و `destroy()` هنگام بستن کانتینر فرصت cleanup می‌دهد. در آزمایش اول، پایان متد `main` به‌تنهایی پیام destroy را نشان نمی‌دهد؛ با `context.close()`، callback اجرا می‌شود. این تفاوت از مهم‌ترین مشاهده‌های عملی درس است.

</SourceBlock>

راه سوم annotationهای `@PostConstruct` و `@PreDestroy` است که در مرور کلاس با نام تاریخی JSR-250 معرفی می‌شوند. در کد فعلی importها از `jakarta.annotation` هستند. با این روش، خود متدها علامت می‌خورند و نام دلخواه آن‌ها معیار زمان اجرا نیست.

استاد توصیه می‌کند این روش‌ها را بی‌دلیل با هم ترکیب نکنیم؛ در صورت نیاز واقعی به چند callback، ترتیب مهم می‌شود: ابتدا PostConstruct، سپس `afterPropertiesSet` و بعد initMethod. در میانهٔ این بحث، تمرین circular dependency جلسهٔ قبل نیز مرور می‌شود؛ setter و lazy در پاسخ‌ها مطرح می‌شوند، اما راهکار سوم در این قسمت با نمونهٔ کامل تشریح نمی‌شود.

## Awareها و shutdown hook؛ دسترسی به کانتینر [#aware-shutdown]

<SourceBlock id="aware-explanation" source="teacher" recording="teacher-05-part2" timestamp="32:20">

کانتینر Beanها را می‌شناسد، اما هر Bean به‌طور عادی لازم نیست از کانتینر سازندهٔ خود خبر داشته باشد. با پیاده‌سازی `ApplicationContextAware`، Spring متد `setApplicationContext` را فراخوانی و context را تحویل می‌دهد. در مثال، از آن برای ثبت shutdown hook استفاده می‌شود.

استاد تأکید می‌کند این دسترسی نباید به عادتِ دریافت دستی همهٔ وابستگی‌ها با `getBean` تبدیل شود؛ روش‌های معمول DI مسئولیت‌ها را روشن‌تر نگه می‌دارند. Awareها برای نیاز به اطلاعات و امکانات زیرساختی کانتینر هستند.

</SourceBlock>

<CodeExample
  id="aware-hook-code"
  source="teacher"

  filename="ShutDownHookBean.java"

  code={

  }
/>

<SourceBlock id="aware-claim" source="teacher" recording="teacher-05-part2" timestamp="36:00">

در توضیح این مثال، مسیر Aware به‌عنوان راه دریافت ApplicationContext معرفی می‌شود و cast به GenericApplicationContext برای رسیدن به `registerShutdownHook()` انجام می‌گیرد. مرور شفاهی shutdown hook نیز ابتدا از پایان غیرعادی JVM مثال می‌زند و سپس به پایین‌آمدن برنامه برمی‌گردد.

</SourceBlock>

<TechnicalCorrection id="aware-api-correction" corrects="aware-claim" statement="در توضیح نمونه، دریافت ApplicationContext با Autowired رد می‌شود و registerShutdownHook به GenericApplicationContext نسبت داده می‌شود." correction="ApplicationContext از وابستگی‌های قابل تزریق خود Spring است و با Autowired هم قابل دریافت است. registerShutdownHook در قرارداد ConfigurableApplicationContext وجود دارد و مخصوص GenericApplicationContext نیست. shutdown hook تضمینی برای crash یا توقف اجباری JVM نیست." reason="برای cleanup قابل اتکا در اجرای معمول، close یا ثبت shutdown hook را صریح انجام دهید؛ به callback هنگام هر نوع توقف تکیه نکنید.">

[قرارداد ConfigurableApplicationContext](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/context/ConfigurableApplicationContext.html)

</TechnicalCorrection>

<SourceBlock id="shutdown-snapshot" source="gpt">

در نسخهٔ ذخیره‌شده، `@Component` روی ShutDownHookBean غیرفعال است و در Test نیز `context.close()` کامنت شده است. بنابراین این نسخه به‌تنهایی ثبت hook نشان‌داده‌شده در ضبط را اجرا نمی‌کند. در بررسی مستقل، با بستن صریح context، PreDestroy مربوط به Human اجرا شد.

برای یک برنامهٔ command-line می‌توان context را در try-with-resources نگه داشت تا پایان محدوده آن را ببندد، یا برای عمر برنامه shutdown hook ثبت کرد. این دو روش را با حذف شیء توسط GC یکی نگیرید. استفاده از context داخل منطق کسب‌وکار نیز موضوع متفاوتی از مدیریت عمر context در نقطهٔ شروع برنامه است.

</SourceBlock>

<SourceBlock id="bean-name-aware" source="teacher" recording="teacher-05-part2" timestamp="40:40">

نمونهٔ دیگر، `BeanNameAware` است: کانتینر از طریق `setBeanName` نامی را که Bean با آن ثبت شده در اختیارش می‌گذارد؛ استاد کاربرد آن را در logging مثال می‌زند. داشتن نام کلاس با دانستن نام ثبت‌شدهٔ Bean یکی نیست. `BeanClassLoaderAware` و Awareهای دیگر نیز برای دسترسی به بخش‌های مشخص زیرساخت معرفی می‌شوند.

تمرین کلاس، ساخت یک Bean آزمایشی با `InitializingBean`، `DisposableBean`، `BeanNameAware`، `BeanClassLoaderAware`، `ApplicationContextAware` و annotationهای lifecycle است تا ترتیب callbackها مشاهده شود. استاد تصریح می‌کند کنار هم گذاشتن همهٔ این‌ها هدف تمرینی دارد؛ نسخهٔ ذخیره‌شدهٔ BeanOne هنوز اسکلت این تمرین است.

</SourceBlock>

در همین کد، دو معنای متفاوت کنار هم‌اند: `List<String>` از List تعریف‌شده دریافت می‌شود؛ اما `List<C04MyBean>` همهٔ Beanهای C04MyBean را جمع می‌کند. بررسی مستقل این snapshot، سه عضو با ترتیب نام‌های `33`، `11` و `22` را نشان داد؛ مطابق `@Order(1)`، `@Order(2)` و `@Order(3)`. عدد کوچک‌تر اول می‌آید. این نتیجهٔ بررسی کد است؛ در ضبط، مثال Order به‌تفصیل اجرا و تدریس نمی‌شود.

`@Order` در این کاربرد ترتیب اعضای collection را مشخص می‌کند؛ برای بیان اینکه یک Bean پیش از دیگری آماده شود، آن را جایگزین `@DependsOn` نکنید. مثال جداگانهٔ Cars نیز در فایل C05Order وجود دارد، ولی scan آن هنوز پکیج قدیمی را دارد و پیش از اجرا باید اصلاح شود.

## تمرین‌ها و ادامهٔ مسیر [#exercises]

<SourceBlock id="teacher-homework" source="teacher" recording="teacher-05-part2" timestamp="01:12:00">

- یک Bean آزمایشی بسازید و ترتیب callbackهای lifecycle، Awareها و متدهای init/destroy را با پیام‌های متمایز مشاهده کنید. ترکیب همهٔ روش‌ها برای شناخت ترتیب است.
- مثال collections را از مخزن بخوانید، مسیرها و پکیج‌های منتقل‌شده را هماهنگ و اجرا کنید؛ نقش ContentHolder و تفاوت ساخت collection در XML و Java را توضیح دهید.

در پایان ضبط، Bean scope، Environment و AOP از مباحث باقی‌مانده معرفی می‌شوند و سپس رفتن به لایهٔ persistence/Spring Data مطرح می‌شود. این برنامهٔ ادامهٔ دوره است؛ این صفحه ادعای پوشش کامل آن مباحث را ندارد.

</SourceBlock>
