## معرفی [#overview]

<SourceBlock id="concept-overview" source="gpt">

تزریق وابستگی یعنی شیء، همکار موردنیازش را از بیرون دریافت کند. مثلاً سرویس انتقال وجه به یک پیاده‌سازی بانک نیاز دارد؛ اگر خودش بانک مشخصی را بسازد، تصمیم انتخاب بانک به منطق سرویس گره می‌خورد. با DI، ساخت و انتخاب این همکار به بخش دیگری از برنامه سپرده می‌شود.

</SourceBlock>

## چرا به آن نیاز داریم؟ [#why]

<SourceBlock id="concept-purpose" source="teacher">

در نسخهٔ دستی جلسهٔ سوم، `BankClient` به قرارداد `ITransferService` متکی است. دو کلاس `MeliImpl` و `MellatImpl` این قرارداد را پیاده‌سازی می‌کنند؛ پیاده‌سازی‌های آموزشی فقط پیام چاپ می‌کنند. در نسخهٔ دستی، `MyContext.injectIn(client)` فیلد را مقداردهی می‌کند؛ در نسخه‌های Spring و Weld، نام رابط `ITransfer` است و کانتینر مسئولیت اتصال را بر عهده دارد.

فایل `my-context.txt` نام پیاده‌سازی را مشخص می‌کند. در پروژهٔ `dependencyInjection-spring6` نیز `@Qualifier("bank1")`، Bean متعلق به `MellatImpl` را انتخاب می‌کند. جزئیات کد در [جلسهٔ سوم سه‌شنبه](/tuesday/session-03/#spring-di) آمده است.

</SourceBlock>

## یک مثال با Java [#java-example]

<SourceBlock id="concept-example" source="gpt">

این مثال مستقل، همان مرز مسئولیت را با تزریق از سازنده نشان می‌دهد؛ بازنویسی عین کد استاد نیست:

```java title="BankClient.java · GPT Example"
interface TransferService {
    boolean transfer(long account, double amount);
}

final class BankClient {
    private final TransferService service;

    BankClient(TransferService service) {
        this.service = java.util.Objects.requireNonNull(service);
    }

    boolean transfer(long account, double amount) {
        return service.transfer(account, amount);
    }
}
```

مصرف‌کننده می‌تواند یک پیاده‌سازی واقعی یا یک بدل آزمایشی دریافت کند. برای فهم DI به Spring نیاز نداریم؛ Spring ساخت و اتصال مجموعهٔ بزرگ‌تری از اشیا را مدیریت می‌کند. [مستندات DI در Spring](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html)

</SourceBlock>

## نکته‌های رایج [#pitfalls]

<SourceBlock id="concept-pitfalls" source="gpt">

- **interface به‌تنهایی DI نیست:** در `TransferService service = new MeliImpl()` هنوز خود مصرف‌کننده پیاده‌سازی را انتخاب می‌کند.
- **Factory به‌تنهایی DI نیست:** اگر مصرف‌کننده از Factory درخواست شیء کند، هنوز منطق یافتن وابستگی داخل مصرف‌کننده است؛ در DI وابستگی به آن داده می‌شود.
- **annotation به‌تنهایی کاری اجرا نمی‌کند:** باید کدی مانند کانتینر آن را بخواند و اتصال را انجام دهد. ساخت `new BankClient()` در بیرون کانتینر الزاماً تزریق Spring را فعال نمی‌کند.
- **DI تمام وابستگی‌ها را حذف نمی‌کند:** برنامه همچنان به قرارداد و رفتار همکار خود وابسته است؛ هدف، روشن‌کردن و کنترل این وابستگی است.

</SourceBlock>

## تفاوت با Service Locator [#service-locator]

<SourceBlock id="concept-locator" source="gpt">

در DI، وابستگی به مصرف‌کننده تحویل داده می‌شود؛ در Service Locator، مصرف‌کننده خودش از یک واسطه درخواست سرویس می‌کند. اولی نیازها را مثلاً در پارامترهای سازنده نشان می‌دهد؛ در دومی باید بدنهٔ کلاس را بخوانیم تا درخواست‌های آن را پیدا کنیم.

این مقایسه دربارهٔ **جهت درخواست** است، نه تضمین زمان ساخت. سرویس درخواست‌شده از locator ممکن است از قبل موجود باشد؛ DI نیز می‌تواند با روش‌های دسترسی تنبل ترکیب شود. [مقایسهٔ دو الگو از مارتین فاولر](https://martinfowler.com/articles/injection.html) و [پرسش‌وپاسخ پنج‌شنبه](/thursday/session-03/#service-locator)

</SourceBlock>

## سازنده یا setter؟ [#injection-timing]

<SourceBlock id="injection-timing-explanation" source="gpt">

در تزریق سازنده، وابستگی هنگام ساخت شیء دریافت می‌شود؛ این الگو برای بیان نیازهای ضروری و امکان نگهداری آن‌ها در فیلد `final` مناسب است. در setter injection، نمونه ابتدا ساخته می‌شود و سپس وابستگی از طریق متد داده می‌شود. این تفاوت ترتیب را با تأخیر خودکار تا بعد از startup اشتباه نگیرید: setter اجباریِ Spring نیز هنگام آماده‌سازی Bean باید وابستگی‌اش را دریافت کند.

در [جلسهٔ چهارم](/tuesday/session-04/#constructor-injection)، یک قرارداد Repository با هر دو روش و با سه نوع پیکربندی متصل می‌شود. انتخاب Oracle یا MySQL به تنظیمات اتصال بستگی دارد؛ روش تزریق به‌تنهایی پیاده‌سازی را انتخاب نمی‌کند. این تصمیم در مرجع [Autowiring](/concepts/autowiring/) توضیح داده شده است.

چرخهٔ سازندهٔ مستقیم میان دو شیء قابل حل نیست؛ بعضی چرخه‌های singleton با setter در Spring Framework قابل اجرا هستند. موفقیت اجرای یک چرخه به معنی طراحی مطلوب یا تضمین رفتار یکسان در تمام تنظیمات نیست. [نمونه و محدودیت چرخه](/tuesday/session-04/#circular-dependencies)

</SourceBlock>
